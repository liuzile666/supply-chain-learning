不用自己养车，也得有一套系统

2026年9月7日 · 第10章 · 三方物流配送系统（p398–408）

今天是第 10 章我最看重的一节。因为拼多多就是这么干的——不养车，但必须把多家物流管明白。

只做三件事

用三方物流就不用管车辆调度、分拣、配送了，系统收窄成三件事：发货前分配物流商并申请电子面单、包裹在途全程跟踪、签收后与物流商对账。

四个模块

  • 基础数据：物流商信息、地址库、面单模板、月结账号。前两者属于全公司公共数据，放基础数据中心共享。
  • 配送策略：策略配置、物流商分配策略、时效承诺、绩效计算。
  • 接口对接：单号申请/取消、状态与轨迹获取、物流拦截查询。
  • 财务结算：运费计算模板、运费及代收货款预算、物流对账。

面单模板要收敛到一处

仓储、配送、门店多个系统都要打面单，如果各做一套就是重复造轮子，而且物流商的面单还在不断升级。好的做法是所有面单模板统一放在配送系统里，由专人维护，外围系统来调用。

月结账号是两用的

物流商给企业开月结账号并提供密钥，它既是结算的唯一账号（不用每单现付，按月对账），也是申请电子面单的令牌。

分配物流：两步走 + 可降级

先按仓配置"这个仓能用哪些物流"，再按策略分配。订单过来时带上发货仓、收件地址、支付方式、代收货款金额、物流付款方式、商品属性，系统①分配物流商 ②获取面单。指定物流商就直接取面单；系统分配则按优先级排序匹配，接口挂了或欠费就切下一家；实在匹配不到还能退回手写面单。

我的连接

这整节就是一个标准的适配器/网关层：把 N 家异构的物流 API 抽象成统一接口，上游只调用一次；分配策略是路由 + 优先级 + fallback，跟我们做服务路由的降级链一模一样。月结账号同时是结算 ID 和 API token，也很有意思——现实中身份和鉴权确实经常是同一个东西。

而"面单模板统一维护"这件事，本质是把易变的外部依赖收敛到一个地方——外部世界会变，变的时候只改一处。这条原则我记住了。

💭 给自己留的话 一家公司同时接十几家物流，每家接口、面单、结算方式都不同——这就是适配器模式最真实的业务场景。
✅ 一句话总结 三方配送系统 = 适配器 + 路由降级 + 对账；面单模板统一维护，把易变的外部依赖收敛到一处。
